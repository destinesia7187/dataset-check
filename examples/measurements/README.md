# Implementation verification results

Measurements were taken on **October 19, 2026**, locally over HTTP on a dedicated server at `127.0.0.1:8001`, with a separate `DATA_DIR`. `performance.json` contains all four iterations (one warm-up and three measured runs), configured limits, versions, and machine details. Environment: Windows 11, Intel Core i5-12450H, 12 logical CPUs, 16 GiB RAM, NVMe SSD INTEL SSDPEKNW512GZL, NTFS, and Python 3.12.14. CPU model and disk type were read using standard Windows queries after the measurements finished.

The benchmark CSV was generated by `scripts/generate_workloads.py` with seed `20261019`: 100,000 records, 20 columns, **12,001,473 bytes**, SHA-256 `da9ad0119626ac09a4053f5a7e1834bf05d4c63dc73cec988e8786e678c22143`. Every field has required-value and type rules; one has a uniqueness rule and five have numeric ranges. Exact duplicate detection is enabled. Expect 90 issues in 60 records.

| Metric | Median of three measured runs |
| --- | ---: |
| POST: transfer + import | 3.468 s |
| Server import after body reception | 3.218 s |
| Analysis including JSON preparation | 1.922 s |
| Page of up to 100 issues | 0.034 s |
| Separate JSON download | 0.044 s |

Isolated import time comes from `Server-Timing: import;dur`; analysis time comes from the server's `duration_ms`. Total client wait duration is recorded separately and includes status polling. The JSON report is 55,373 bytes. All three specification performance targets were met on this machine. These results do not guarantee the same speed for other inputs, issue counts, or hardware.

To reproduce the measurements with a dedicated server running:

```powershell
python scripts/generate_workloads.py
python scripts/benchmark.py --url http://127.0.0.1:8001 --disk "your disk model" --output benchmark-results/performance.json
python scripts/check_budgets.py --url http://127.0.0.1:8001
```

The separate default-budget scenario was also executed: exactly 100,000 issues succeeded; 100,001 failed with `RESULT_LIMIT_EXCEEDED` and no summary or export; the stress dataset of 100,000 × 20 values of `x`, with potentially 4.1 million issues, produced the same controlled failure; a subsequent run with 100,000 issues succeeded. Each created dataset was deleted after its scenario. Reduced temporary limits were not used for this check.

`browser-e2e.json` records a real browser scenario using Microsoft Edge, Playwright 1.58.2, and the built frontend at `127.0.0.1:8765`. Through the interface, it uploaded the acceptance CSV, configured rules, verified the 13/8 result, filtered issues, viewed a record and duplicate group, downloaded JSON, and reloaded the page to restore the original rules. No unhandled JavaScript errors occurred. UUIDs identify demonstration resources; the dataset was deleted afterward.
